# 09 — Security, Testing, Demo Mode & Test Lab

## 1. Security checklist (must all be true at the end)

**Authentication / sessions**
- [ ] Passwords hashed with argon2id; min length 10; login rate-limited (5/min/IP+email).
- [ ] JWT in httpOnly, Secure (in prod), SameSite=Lax cookie; 8 h expiry; logout clears it.
- [ ] CSRF: state-changing endpoints require header `X-Requested-With: ec2opt` (simple double-check) or CSRF token.
- [ ] CORS restricted to `FRONTEND_ORIGIN`.

**AWS access**
- [ ] No AWS access/secret keys are accepted by any endpoint or stored anywhere (grep test in CI: fail if "AKIA" pattern appears in DB seed/code).
- [ ] External ID is server-generated, unique, never reused across connections.
- [ ] Temporary credentials only in Redis (encrypted), TTL ≤ session expiry, never logged.
- [ ] Platform keys (dev only) come from env; in production the instance/task role is used; `.env` is git-ignored.
- [ ] Every API query is scoped to the authenticated user's connections (tests for cross-tenant access → 404).

**Actions**
- [ ] Read-only by default; actions need explicit enable + DryRun probe.
- [ ] Preview → confirm → async execute → audit → undo (doc 05).
- [ ] Rate limit 10 actions/user/hour; one active action per instance.

**Other**
- [ ] Input validation on all bodies (Pydantic); ARN regex; instance IDs `^i-[0-9a-f]{8,17}$`; region whitelist from `describe_regions`.
- [ ] Security headers (CSP, X-Content-Type-Options, X-Frame-Options) via middleware / nginx.
- [ ] Dependencies pinned; `pip-audit` / `npm audit` documented in README.
- [ ] Logs never contain role credentials, passwords, or cookies.
- [ ] "Delete account" and "Disconnect" really delete related rows.

## 3. DEMO_MODE (mandatory)

`DEMO_MODE=true` means **no boto3 call is made anywhere**.
- `POST /connections/demo` creates a connection with `status=connected`, `aws_account_id="000000000000"`, `enable_actions=true`.
- `run_scan` loads `backend/app/pipeline/demo_fixtures.json` (≈ 14 instances) instead of calling AWS. Include at least:
  | # | Instance | Status | Notes |
  |---|---|---|---|
  | 1–2 | idle `dev-sandbox`, `old-poc` | IDLE | one t3.large, one m5.xlarge |
  | 3 | `db-replica-1` | NEEDS_REVIEW | blocked by sensitive tag `replica` |
  | 4–7 | app/worker servers | OVER_PROVISIONED | m5.2xlarge→m5.large, c5.4xlarge→c5.xlarge, one memory not checked (LOW confidence), one T-family |
  | 8–9 | `api-gateway`, `batch-runner` | UNDER_PROVISIONED | one CPU-saturated, one credit-starved t3.micro (→ unlimited credits) |
  | 10–12 | healthy servers | ACTIVE | |
  | 13 | stopped instance | STOPPED | |
  | 14 | new instance | INSUFFICIENT_DATA | |
  Each fixture contains full `evidence_steps`, `metrics`, 14 days of plausible `hourly_series` (daily seasonality + noise), and a `suggestion` object consistent with doc 04 §5.
- `demo_service` fake executor: applies actions to an in-DB "fake instance state" (sleep ~1 s per step) so Apply / Undo / rollback (one fixture instance configured to fail on resize → shows rollback UI) all work.
- Seed the `savings_ledger` with ~60 days of history for the demo user so the dashboard charts are rich.
- A seed command: `docker compose exec api python -m app.scripts.seed_demo` creates `demo@example.com / DemoPass123!`.

## 4. Real-AWS test lab (for the FYP evaluation chapter)

Purpose: produce **ground-truth labelled instances** to measure the detector (precision/recall, confusion matrix). Put in `docs/LAB.md` generated by Claude Code (steps below), in a throw-away AWS account/region, with a billing alarm.

| Lab instance | Type | What to run | Expected label |
|---|---|---|---|
| lab-idle | t3.medium | nothing (OS only) | IDLE |
| lab-idle-protected | t3.medium | nothing, tag `Role=db-replica` | NEEDS_REVIEW |
| lab-over | m5.xlarge | `stress-ng --cpu 1 --cpu-load 15 -t 0` (≈ 4 % of 4 vCPU, tiny peaks) + light web traffic | OVER_PROVISIONED |
| lab-under | t3.small | `stress-ng --cpu 2 --cpu-load 95 -t 0` | UNDER_PROVISIONED |
| lab-credit-starved | t3.micro | 100 % CPU in *standard* credit mode until credits drain | UNDER_PROVISIONED (credit rule) |
| lab-active | t3.medium | `stress-ng --cpu 1 --cpu-load 40` | ACTIVE |

All with the CloudWatch Agent installed (mem metric) except one extra copy of `lab-over` *without* it to demonstrate the lower-confidence path. Install snippet for the agent (Amazon Linux 2023):
```bash
sudo dnf install -y amazon-cloudwatch-agent stress-ng
cat <<'EOF' | sudo tee /opt/aws/amazon-cloudwatch-agent/etc/config.json
{"metrics":{"append_dimensions":{"InstanceId":"${aws:InstanceId}"},
 "metrics_collected":{"mem":{"measurement":["mem_used_percent"],"metrics_collection_interval":60}}}}
EOF
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -c file:/opt/aws/amazon-cloudwatch-agent/etc/config.json -s
```
(The instance needs an instance profile with `CloudWatchAgentServerPolicy`.)

Note: with the production setting (`LOOKBACK_HOURS=336`, `MIN_HISTORY_HOURS=168`, `APPLY_DATA_QUALITY=true`) lab instances need to run ≥ 7 days for full confidence. For quick demos use dev settings (`LOOKBACK_HOURS=35`, `MIN_HISTORY_HOURS=20`, `APPLY_DATA_QUALITY=false`), which is what the detector's inline comments describe.

Evaluation script `backend/scripts/evaluate.py`: reads a CSV of `instance_id,expected_label`, runs a scan, outputs confusion matrix + per-class precision/recall to `evaluation_report.md` (useful for the FYP report).

## 5. Cost-of-running notes (put in README)
- `GetMetricData` is billed per metric requested (~8–12 metrics per instance per scan); daily scans of 50 instances is cents/month, but state it.
- Pricing API calls are free; results cached 7 days.
- Recommend running the platform on a single small VM (Docker Compose) for the FYP demo.
